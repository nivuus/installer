# Host network: RF map, VM wake-on-demand, WAN / PPPoE

### RF / Radio Frequency Map (2.4 GHz coexistence plan)

Audited 2026-07-16 — current layout has **zero overlap**, preserve it:
- **WiFi 2.4 GHz**: QCA9984 (`phy2`, `wlp11s0`+`wlp11s1`) — **ch 6 pinned** (2427–2447 MHz), 20 MHz, 20 dBm (also forced by an `ExecStartPost` in hostapd.service). 2026-07-16: `channel=6` pinned (was `0` = ACS, which could land on ch 9–11 = on Thread) and `[HT40+]` removed (its secondary channel ch 10 @ 2457 MHz would cover Thread) in `/etc/hostapd/2.4Ghz.conf`. Card EEPROM regdom is US → ch 12/13 unavailable. NB: `systemctl reload hostapd` (HostapdManager's apply path) cannot apply channel/BSS changes — those need `restart` (~10 s outage, clients re-attach automatically).
- **WiFi 5 GHz**: QCA9984 (`phy1`, `wlp10s0`+`wlp10s1`) — ch 36 fixed, VHT80 centered ch 42 (5170–5250 MHz, UNII-1 non-DFS), 23 dBm. Cards support VHT160 but that requires DFS channels (radar interruptions) — 80 MHz is the deliberate stability choice.
- **Zigbee**: zigbee2mqtt, **ch 25 (2475 MHz)**, 20 dBm, `adapter: zstack` on SMLIGHT **SLZB-MR2U** USB stick interface `if02` (`ttyACM2`).
- **Thread**: OTBR container (host network, `wpan0`), **ch 21 (2455 MHz)**, txpower **+20 dBm** (stick max, ETSI-legal; was 0 until 2026-07-16 — raised because child 0xe807 at RSSI −77 dropped downlink frames). otbr-agent does NOT persist txpower — it is applied by the `command` override on the `otbr` service in `/opt/nivuus/HomeAssistant/docker-compose.yml` (s6-overlay runs it after services; loop re-applies every 5 min). Thread dataset persists in `/opt/nivuus/HomeAssistant/otbr` → recreating the container is safe. RCP on the **same SLZB-MR2U stick** `if00` (`ttyACM0`) — it is a dual-radio stick.
- **Bluetooth**: Intel AX201 (`hci0`, name `nivuus`), BLE central+peripheral, AFH across 2402–2480. The AX201 WiFi half (`wlo1`) is unused (down, NM-unmanaged).
- No RF hardware passed to the Windows VM (GPU + audio + one Samsung NVMe only). No DVB/Z-Wave/LoRa hardware.

### VM Wake-on-Demand (cloud gaming)

`vm-trigger-47984.socket` **and `vm-trigger-47989.socket`** (added 2026-07-17 so that merely *opening* Moonlight — which polls serverinfo on 47989 HTTP and/or 47984 HTTPS — wakes the VM; clients must target the HOST LAN IP `192.168.0.1`, not the VM IP, and re-pair once against that entry) (systemd socket-activation, host `0.0.0.0`, `Accept=false`) trigger the oneshot `vm-trigger-{port}.service` → `/usr/local/sbin/vm-wake-gate.py` (**wake gate**, 2026-07-17, source of truth now `console/host/vm-wake-gate.py` + `console/tests/test_vm_wake_gate.py`: accepts the pending connection, reads the first bytes, only chains to the wake script if the client speaks Moonlight; port scans/mute connections are logged `wake REJECTED from <ip>` and ignored; syslog tags `vm-wake-gate-{port}`) → `/usr/local/sbin/handle-vm-start.sh`: starts the Windows VM if shut off, waits for its IP (agent then DHCP lease, 180s max), then adds a **runtime** forward-port in the **default** firewalld zone.

**The wake sockets ARE internet-exposed while the VM is off (CRITICAL, found 2026-07-24 — the opposite of what this file claimed).** The belief that "the permanent `external` DNAT `47984/47989→192.168.3.2` means WAN traffic never reaches the host socket" is **wrong**: the libvirt hook `qemu.d/Windows/stopped/end/rules.sh` deletes those forward-ports **from every active zone** when the VM stops (they are re-added by `started/begin/rules.sh`). So exactly when the wake path is armed, the DNAT is gone and the whole internet can reach `0.0.0.0:47984/47989` on `ppp0`. Consequence: **the 47984 test (`data[0] == 0x16`, i.e. "client speaks TLS") matched every mass scanner on the internet.** Over the 30 days to 2026-07-24, *all* wakes it produced were false positives (Driftnet, Linode, Akamai, Datacamp, …) and *zero* came from a real client; the only genuine wakes came from 47989 with `GET /serverinfo`. **Fix: 47984 is out of the wake path** (probes still logged); 47989's HTTP signature is the only wake trigger — proven discriminator, 42 scanner probes rejected, 0 false positive. Remote (off-LAN) wake still works because Moonlight also probes 47989. Residual risk: a scanner that deliberately speaks Sunshine/Moonlight HTTP would still wake the VM — for strict control add a firewalld source-IP allowlist (breaks roaming clients). Diagnostic reflex: `journalctl -t vm-wake-gate-47984 -t vm-wake-gate-47989 | grep accepted` shows the source IP of every wake; `grep dport=4798 /proc/net/nf_conntrack` shows the live scan traffic. `Type=oneshot` + repeated triggering (even *successful* runs — systemd counts starts, not failures: ≥5 Moonlight polls in 10 s during a VM boot window trip it) killed the socket via `service-start-limit-hit` (2026-07-13, again 2026-07-17). **Fixed permanently 2026-07-17**: drop-ins `no-start-limit.conf` (`StartLimitIntervalSec=0`) on both trigger services, `flock` single-instance guard in `handle-vm-start.sh`, and transitional-state handling (waits up to 90 s for `in shutdown`/hibernation to settle instead of exit 1). The idle-check timer also self-heals both sockets every 10 min whenever the VM is off. Manual recovery if ever needed: `systemctl reset-failed vm-trigger-{47984,47989}.{service,socket} && systemctl start vm-trigger-{47984,47989}.socket`.

### WAN / PPPoE (Orange/Sosh fibre) — CRITICAL

The WAN is a PPPoE session over VLAN 835. **The physical WAN port is now `enp5s0` → VLAN `enp5s0.835`** (was historically `enp6s0.835`; the cable/port moved). NM still manages the VLAN `enp5s0.835` and brings it up at boot.

**Boot persistence is handled by NetworkManager** (profile `pppoe-enp6s0.835`, autoconnect=yes, zone=external):
- The **critical config** for PPPoE-over-VLAN with NM is to set **BOTH** `connection.interface-name=ppp0` (the ppp device NM creates) **AND** `pppoe.parent=enp5s0.835` (the VLAN). NM does support a VLAN parent (the earlier "RH bug 1663719 / unsupported" belief was wrong — the real cause was an *empty* `connection.interface-name`, which yields `error determine name for pppoe`; setting `interface-name` to the VLAN device instead yields `No suitable device found ... mismatching interface name`). Validated 2026-05-25.
- The HA `PppoeCredentials.ts` integration edits this nmconnection file for credentials; NM now actually brings up the link.
- **Fallback (kept, disabled):** systemd unit `/etc/systemd/system/pppoe-dsl.service` runs `pppd call dsl-provider persist holdoff 60 maxfail 0 nodetach` over peer file `/etc/ppp/peers/dsl-provider` (`pty "pppoe -I enp5s0.835 ..."`, `user "fti/CHANGE_ME"`, CHAP via `/etc/ppp/chap-secrets` + `/etc/ppp/pap-secrets`). If NM ever fails: `nmcli con down pppoe-enp6s0.835 && systemctl start pppoe-dsl.service`. Do NOT run both at once (they fight for the enp5s0.835 PPPoE session).

**Orange BNG reconnect cooldown (IMPORTANT):** after a clean pppd teardown (SIGTERM → PADT), Orange holds the session ~3-5 min and rejects fast reconnects (CHAP fails even with the right password). **Never hammer reconnects** — that is why the unit uses `RestartSec=120` + pppd `holdoff 60` + `persist` (persist redials without a clean PADT). When recovering manually after a kill, wait ~5 min before relaunching.

**Firewalld zone for ppp0:** `ppp0` is dynamic and must be placed in the `external` zone, done by `/etc/ppp/ip-up.d/firewalld-external` on every link-up. Without it, ppp0 falls into the default `internal` zone (too permissive for WAN) AND the external-zone forward-ports (cloud-gaming → 192.168.3.2) don't apply. firewalld uses the **nftables** backend (`table inet firewalld`) — `iptables -t nat -S` looks empty but isn't; check `nft list table inet firewalld`. `net.ipv4.ip_forward` is already persistent in `/etc/sysctl.conf`.

**WAN receive processing is pinned to the E-cores (2026-08-26).** As far as the NIC is concerned a PPPoE session is one flow, so every inbound packet landed on one hardware queue and one CPU — and that CPU was the ceiling, not the line. Measured against `ash-speed.hetzner.com`, four alternating passes: **147/121/137/122 Mbit/s with RPS off** (cpu17 alone at 26-29 % softirq) against **203/235/180/227 Mbit/s with RPS on** — **+60 %, for one sysfs write**. `/etc/ppp/ip-up.d/nivuus-rps-ecores` (repo: `configs/network/ppp-ip-up.d/`) runs `/usr/local/bin/net-rps-ecores.sh apply ppp0` at every link-up, because ppp0 is destroyed and recreated with `rps_cpus` back to 0 on each reconnection — a boot-time one-shot would silently stop applying after the first Orange cooldown. The script picks the E-cores by their lower max frequency, never hard-coded (this box has no `/sys/devices/system/cpu/types` to ask); tests in `scripts/tests/test_net_rps_ecores.sh`. **RPS cannot split a single TCP flow across cores** (it would reorder packets): the gain comes from moving the TCP/IP half off the core doing PPPoE decapsulation, so a mono-flow download still has one hot core — it is just no longer doing all the work alone.

**WAN egress is shaped by CAKE (2026-10-11).** `/etc/ppp/ip-up.d/nivuus-wan-cake` (repo: `configs/network/ppp-ip-up.d/`) attaches `cake bandwidth 780mbit besteffort nat dual-srchost overhead 50 mpu 84` to ppp0 at every link-up, for the same reason as the RPS hook: ppp0 comes back with a bare `noqueue`. Unshaped, a saturated uplink queued in the ONT/at Orange: Ookla against Scaleway Paris, four alternating passes, **up 802/801 Mbit/s at 65/55 ms under load (peaks 463/251 ms, 4.9 % ping loss)** against **722/721 Mbit/s at 10/10 ms (peaks 12 ms)** shaped; download identical either way (925-935 Mbit/s, capped by the 1 Gbit/s link to the ONT). The rate is a property of the subscription, not derivable on the host: override `RATE` in `/etc/default/nivuus-wan-cake` if the offer changes, and keep it below the real uplink or the queue moves back upstream. Ingress is deliberately not shaped (+13 ms under load, not worth an IFB and the throughput). Verified on real PPPoE reconnections the same day: the qdisc, the RPS mask and the `external` zone all came back by themselves.

**firewalld restarts on failure (2026-10-11).** The packaged unit has no `Restart=`. A mass SIGKILL at 18:08 that day took down 51 services; everything carrying `Restart=` was back within seconds, firewalld stayed dead for ten minutes. Its nftables table outlives the daemon, so filtering and NAT held, but no interface could be given a zone and every `firewall-cmd` caller failed. Drop-in `/etc/systemd/system/firewalld.service.d/10-nivuus-restart.conf` (repo: `configs/systemd/firewalld.service.d/`) sets `Restart=on-failure`, `RestartSec=2`; proven by `kill -9`: back in 10 s with every interface in its zone. Known cost: a restarted firewalld rebuilds from the permanent configuration, so the runtime-only cloud-gaming forward-ports added by the libvirt hooks are lost until the next VM start. After any incident, list failed units over D-Bus (`ListUnitsFiltered array:string:"failed"`): 19 other units without `Restart=` had stayed down too.

**Every IRQ is banned from the P-cores (2026-08-26).** `IRQBALANCE_BANNED_CPULIST=0-15` in `/etc/default/irqbalance` (repo: `configs/cpu/irqbalance-default.conf`; original kept as `/etc/default/irqbalance.avant-ban-pcores`). irqbalance had piled **98 IRQ onto cpu0 alone** — ahci (304 M interrupts), the three `enp5s0` queues (420 M together), xhci (34 M), the nvme admin queue — and cpu0 is pinned by the Windows VM whenever it runs, so every one of those fired straight into a live vCPU while gaming. The cpuset partitioning in `vm-cpu-partition.sh` never covered this: **IRQ are not subject to cgroups**, which is exactly why the hole went unnoticed. After the ban: **0 IRQ left on cpu0-15, 205 on the E-cores**, NVMe direct read unchanged at 1.6 GB/s, no failed unit. Kernel-managed IRQ (nvme io queues) are out of irqbalance's reach either way and the kernel already spreads them.

**Recovery if internet is down at boot:** `sudo nmcli connection up pppoe-enp6s0.835` (after a ~5 min wait if Orange is in cooldown). Last-resort fallback: `sudo systemctl start pppoe-dsl.service` (disable NM autoconnect first to avoid a fight: `nmcli con modify pppoe-enp6s0.835 connection.autoconnect no`). The bridges/WiFi (localBridge/publicBridge/internalBridge) are NM-managed and rebuild cleanly on a full reboot — a NM *restart* (not reboot) can orphan localBridge's members (hostapd wlp10s0/wlp11s0 + enp14s0), breaking home WiFi; a reboot fixes it.

**Orange DHCP WAN (VLAN 832), staged 2026-10-11, not yet in service.** Design: `docs/superpowers/specs/2026-10-11-wan-orange-dhcp-design.md`. Deployed and **disabled**: `nivuus-wan-orange.service` (VLAN, `tc` 802.1p marking, zone, CAKE; script `/usr/local/sbin/nivuus-wan-orange.sh`), `nivuus-wan-orange-dhcp{4,6}.service` (ISC dhclient in the foreground), `nivuus-wan-orange-check.timer`. NetworkManager ignores `enp5s0.832` through a `[device-*]` section in `conf.d/nivuus-wan-orange.conf` — never a second `unmanaged-devices=` key, which would replace the list in `base.conf` and hand the Wi-Fi interfaces back to it. **dhclient is confined by AppArmor (`usr.sbin.dhclient`): it reads its configuration only under `/etc/dhcp/` and writes its PID only as `/run/dhclient*.pid`. Anywhere else it reports nothing and starts on its defaults**, sending none of the options Orange authenticates on — so the options are rendered to `/etc/dhcp/nivuus-orange/` at every start, and `scripts/tests/test_orange_dhclient_wire.sh` reads the real DISCOVER and Solicit off a veth. What still names `ppp0` and was left alone: `/etc/mqtt-system-agent/config.yaml` (monitored interfaces; follow-up in `nivuus/mqtt`), `/etc/suricata/*` (not running), `/etc/ppp/ip-up.d/*` and `/usr/local/bin/net-rps-ecores.sh` (PPPoE only, kept for the rollback), the three IPv6 `-i ppp0` direct rules (IPv6 forwarding belongs to the second plan). Already taught the new interface: the three IPv4 direct rules, `dhcpv6-client` in the `external` zone, and `inet nivuus_smb`.

**First real attempt on VLAN 832, 2026-10-11 19:00 — unplanned, and Orange parked the client.** A test suite for `wan-cutover.sh` was run against a version of the script that ignored the test seam (`NIVUUS_TEST_PATH`): the fakes were bypassed and the test performed a real cutover as root, then was killed by a timeout before its rollback. What the attempt measured: DHCPv6 works — `fe80::ba0:bab` advertised and granted `2a01:cb14:9009:5400::/56`; **DHCPv4 was parked from the very first OFFER** (`172.16.x.y` from `80.10.233.133`, a different address each time, REQUESTs never acknowledged), before the DHCPv6 client had sent anything, so the then-unfixed "one salt per protocol" defect is not the cause. Ruled out in the lab since: the 802.1p priority of real `dhclient` frames (6 for DISCOVER and Solicit through the prepared VLAN) and the presence of options 60/61/77/90/55 on the wire. **Not yet explained**: the hand-built DISCOVER of 18:01 got a public OFFER and the one `dhclient` sent did not. The next attempt must capture the OFFER (`tcpdump -vv`; option 125 carries the cause code Orange returns) before anything else is changed, and **the cutover must not be run for real until that is explained**. Other defects that run exposed, all fixed and tested: the liveness check restarted both clients every 150 s while they had no lease; `dhclient -6` died at start on a link-local still in duplicate address detection; `Environment=IF_METRIC` never reached `dhclient-script`.

**How the staged pieces fit since the review of 2026-10-11.** `nivuus-wan-orange-options.service` renders both `dhclient` configurations in one call, from one salt: option 90 (v4) and option 11 (v6) must carry the same bytes, and two renders would not. The liveness check probes the gateway by ARP (`arping`), never ICMP, and leaves a client that has no default route yet alone. `nivuus-wan-cutover.sh to-dhcp` changes nothing persistent (unit enablement, PPPoE `autoconnect no`) until an HTTP 204 came back through `enp5s0.832`; until then a reboot still finds PPPoE. Its rollback never re-activates a PPPoE session that is already up (`nmcli con up` on a live session tears it down and starts the Orange cooldown).

**Why Orange parked the client: the DISCOVER left with 802.1p priority 0 (found 2026-10-11, two planned outages of 318 s).** The same hand-built DISCOVER got a public OFFER (`2.3.59.213`, option 125 `…0a0001 0000…`) on a bare VLAN interface and a parked one (`172.16.x.y`, option 125 `…0a0001 000199…`) through the production interface, with IPv6 entirely off: the capture shows `p 6` on the first and `p 0` on the second. `dhclient` was innocent. Cause: `enp5s0` (igc) has **`tx-vlan-offload` off**, so the VLAN device announces an 18-byte link header, and a frame written whole on a packet socket — how `dhclient -4` sends — carries a network-header offset 4 bytes too far. `tc flower` parses from that offset, missed the frame, and the catch-all rule reset its priority to 0. Kernel-originated frames (ARP, ND, a UDP socket) were marked correctly, which is why the earlier proof passed: it was made on a veth (hardware tagging) with a UDP socket — **a test that could not fail the way production does**. The marking is now an nftables `netdev` egress hook (`table netdev nivuus_wan_orange`) matching from the link-layer header (`@ll`), and `test_wan_orange_cos.sh` runs on a dummy parent (no hardware tagging, like igc) and sends the DISCOVER from a packet socket. `ethtool` is not installed on the host; the offload state was read with the `ETHTOOL_GFLAGS` ioctl. Not yet done: the real cutover with this fix.

**IPv6 on the Orange link: the prefix is delegated, the gateway does not answer yet (probed 2026-10-11, nothing deployed).** DHCPv6 works: `fe80::ba0:bab` sends Advertise and Reply, and the `/56` is recorded in `/run/nivuus/wan-orange.prefix`. But a Router Solicitation gets no Router Advertisement (three tries, plus 75 s of passive listening), and a Neighbor Solicitation for `fe80::ba0:bab` gets no answer (`ip -6 neigh`: `FAILED`), although both leave the wire tagged priority 6 (captured on `enp5s0`). So there is no IPv6 default route to install yet, by RA or by hand. The usual recipe (Vincent Bernat's Linux setup: `accept_ra=2` on the WAN, `rdisc6`, one `/64` per LAN, dnsmasq for the RAs) assumes that RA arrives. Open before any LAN plan: find why ND is silent (does Orange need a fresh DHCPv6 exchange rather than the INIT-REBOOT confirm the client did after the 19:59 restart, a reboot of the ONT, or something else in the frames). Other things the probes showed: nothing on the host sends RAs today (`radvd` not installed; the three dnsmasq are NetworkManager's `shared` IPv4 ones), `localBridge` already carries a ULA `/64`, and the `external` zone rejects by default. Not WAN-related but found on the way: `suricata.service` names `ppp0` but is disabled and has never logged anything; the MQTT agent discovers interfaces only at start, so it had to be restarted to publish `enp5s0.832`.

**Orange opens neighbour discovery only after a full DHCPv6 exchange (2026-10-11 20:15).** Restarting `nivuus-wan-orange-dhcp6.service` alone (its `ExecStop` releases, so the next start Solicits) settled the question above: one second after the Reply, `fe80::ba0:bab` sent an unsolicited Router Advertisement (router lifetime 4500 s, MTU 1540, no prefix, M and O clear), then answered a Router Solicitation, a Neighbor Solicitation and echo requests. The silence before came from the 19:59 restart: the interface had been deleted under the client, the release never left, and the next start only Confirmed the lease (INIT-REBOOT), which Orange acknowledges without reopening ND. **Consequence for the LAN plan: any start that finds a lease file (a reboot, a crash) takes that Confirm path**, so the client must be made to Solicit on every start, and the check must test ND, not just the presence of a prefix. IPv4 was untouched by the restart. The stale `2a01:cb14:9009:5400::/56` is still requested by the client and still has its `unreachable` route.

**IPv6 for the LANs is one unit, `nivuus-wan-orange-lan6.service`** (`scripts/wan_orange_lan6.py`, deployed as `/usr/local/sbin/nivuus-wan-orange-lan6.py`). Every 15 s it sets `accept_ra=2` on the WAN so the kernel learns the default route from Orange's advertisement (soliciting one with `rdisc6` when there is none), puts `<prefix>:<index>::1/64` on each bridge listed in `/etc/nivuus/wan-orange-lan6.conf` (`localBridge 0`, `publicBridge 2`: the index is the IPv4 third octet), and runs `nivuus-lan6-radvd.service` on a configuration rendered in `/run/nivuus/radvd.conf`. No prefix or no default route: nothing is handed out. A gateway silent to `ndisc6` four runs in a row gets the DHCPv6 client restarted, which is the full exchange Orange needs. **Enabled, it follows the DHCPv6 client (`WantedBy` and `PartOf` it); to turn LAN IPv6 off, disable and stop it**: the loop withdraws the addresses and stops radvd, whose last advertisement deprecates the prefixes. `radvd` and `ndisc6` are host packages installed by hand; the packaged `radvd.service` stays disabled.
